第一章：无符号整数（size_t / unsigned）陷阱

核心问题：无符号整数（unsigned）在运算时永远不会小于 0，一旦发生减法下溢，会变成一个极其巨大的正数。

1. 容器大小与 int 混用

  • 场景：vector.size()、string.size()、strlen() 返回的都是 size_t（无符号）。
  • 致命错误：for (int i = 0; i < v.size() - 1; ++i)。当 v 为空时，v.size() - 1 变成 $2^{64}-1$，导致死循环或越界 RE。
  • 正确写法：int len = (int)v.size(); for (int i = 0; i < len; ++i)

2. 倒序循环

  • 致命错误：for (int i = v.size() - 1; i >= 0; --i)。当 i 减到 0 后再 --i 变成 -1，与 size_t 比较时 -1 被转换成极大正数，循环永不结束。
  • 正确写法：for (int i = (int)v.size() - 1; i >= 0; --i)

3. 二分查找死循环

  • 场景：手写二分时，mid = (l + r) / 2。如果 l 和 r 都是 unsigned，且 l + r 溢出，mid 会变得很小。
  • 正确写法：使用 mid = l + (r - l) / 2。

第二章：数据溢出与精度陷阱

1. int 溢出（爆 int）

  • 场景：计算 $N \times M$，$N, M \le 10^5$。结果 $10^{10}$，超出 int 上限（$2.1 \times 10^9$）。
  • 致命错误：int ans = n * m;
  • 正确写法：long long ans = 1LL * n * m;（乘法前先强制转换一个乘数为 long long）。

2. 浮点数判等

  • 致命错误：if (a == b) 或 if (a + b == c)。浮点数计算有精度误差，比如 0.1 + 0.2 != 0.3。
  • 正确写法：if (fabs(a - b) < 1e-8)。

3. 取模减法为负

  • 致命错误：ans = (a - b) % MOD;。如果 a < b，ans 会是负数，导致 WA。
  • 正确写法：ans = ((a - b) % MOD + MOD) % MOD;

4. 常量定义的坑

  • 致命错误：const int MOD = 1e9 + 7;。1e9 是浮点数（double），赋值给 int 虽然会隐式转换，但可能在某些编译器下丢失精度。
  • 正确写法：const int MOD = 1000000007;（C++11 后 1e9 + 7 通常安全，但建议写全）。

第三章：数组与内存陷阱

1. 栈溢出（爆栈）

  • 场景：在 main 函数内部定义大数组，如 int a[1000005];。
  • 原因：函数内的局部变量存储在栈上，栈空间通常只有 1MB~8MB。大数组会导致 RE。
  • 正确做法：将大数组定义为全局变量（全局区有 256MB+），或者使用 static 关键字。

2. memset 的误用

  • 致命错误：memset(a, 1, sizeof(a))。memset 是按字节赋值的。把每个字节设为 1，一个 int（4字节）会变成 0x01010101（即 16843009），而不是 1。
  • 正确用法：memset 只能用于赋 0、-1（因为补码全 1）或 0x3f（用于初始化为无穷大）。赋其他值请用 fill() 或循环。

3. 数组开小

  • 场景：题目要求 $N \le 10^5$，你开了 const int MAXN = 1e4 + 10;。
  • 后果：本地小数据能过，评测机大数据直接 RE 或 WA。数组宁可开大 10 倍，不可开小 1 个。

第四章：输入输出与缓冲区陷阱

1. cin/cout 与 scanf/printf 混用

  • 后果：开启 ios::sync_with_stdio(false) 后混用 getchar() 或 scanf，会导致输入缓冲区错乱，产生玄学 WA。
  • 原则：要么全用 C++ 流，要么全用 C 标准 I/O。

2. 多组数据不清空

  • 场景：题目有多组测试数据（while (cin >> n) 或 T 组）。
  • 后果：上一组的数组、vector、map 还残留着数据，导致下一组答案错误。
  • 正确做法：每组数据前清空 vector、map、重置 dp 数组。

3. getline 读到空行

  • 场景：cin >> n; getline(cin, s);
  • 原因：cin >> n 读完后，缓冲区残留 \n，getline 读入这个空行。
  • 正确做法：cin >> n; cin.ignore(); getline(cin, s);

第五章：STL 容器陷阱

1. vector 遍历时删除元素

  • 致命错误：for (auto it = v.begin(); it != v.end(); ++it) { if (...) v.erase(it); }。erase 后迭代器失效，++it 会导致 RE。
  • 正确写法：v.erase(remove_if(...), v.end()) 或 it = v.erase(it)。

2. map 的 [] 访问

  • 场景：map<int, int> mp; if (mp[x] == 0) ...
  • 后果：如果 x 不存在，mp[x] 会插入一个键为 x、值为 0 的元素。这会改变 map 的大小，如果后面遍历 map，会多出无意义的元素。
  • 正确做法：查询用 mp.count(x) 或 mp.find(x)。

3. priority_queue 默认是大根堆

  • 场景：Dijkstra 算法或需要小根堆。
  • 正确写法：priority_queue<int, vector<int>, greater<int>> q;（注意 >> 在 C++11 前要加空格 > >）。

第六章：宏定义与函数陷阱

1. 宏定义重复计算

  • 致命错误：#define max(a, b) a > b ? a : b。调用 max(i++, j) 时，i++ 会被执行两次。
  • 正确做法：使用 inline 函数，或加括号 #define max(a,b) ((a) > (b) ? (a) : (b))。

2. 宏名冲突

  • 场景：在 Windows 下，<windows.h> 定义了 max 和 min 宏。如果你写了 #define max(a,b) ...，会引发冲突。
  • 正确做法：不要自己定义 max 和 min，直接使用 std::max 和 std::min。

第七章：递归与栈溢出陷阱

1. DFS 递归过深

  • 场景：图论题中，递归深度达到 $10^5$ 级别。
  • 后果：栈溢出 RE。
  • 正确做法：改写成栈（stack）迭代，或者手动开大编译器栈空间（如 -Wl,--stack=268435456，但评测机不一定支持）。

2. 忘记回溯

  • 场景：DFS 求全排列、N 皇后。
  • 后果：标记数组 vis[i] = 1 后没有恢复 vis[i] = 0，导致后续搜索无法使用该元素。
  • 正确做法：在递归返回后，立即恢复现场。

第八章：string::size()、strlen(s)

std::string::size() 的时间复杂度是 $O(1)$（常数时间）。

一、为什么是 O(1)？（底层原理）

std::string 在底层实现时，内部通常会维护三个指针（或者一个指针+两个长度变量）：

  1. _M_dataplus（指向字符串数据的指针）
  2. _M_string_length（当前字符串的长度，直接存下来了）
  3. _M_allocated_capacity（当前分配的容量）

当你调用 s.size() 时，它只是直接返回这个已经存好的变量，不需要像 C 语言那样从头到尾遍历去数。所以无论字符串多长，耗时都是固定的。

二、与 C 风格字符串的致命对比（竞赛避坑）

这是复赛中最容易导致 TLE（超时）的隐形杀手：

  • std::string s; s.size() → $O(1)$
  • char s[MAXN]; strlen(s); → $O(N)$（strlen 必须从头遍历到 \0）

复赛经典惨案：如果在 for 循环里写 for (int i = 0; i < strlen(s); ++i)，每次循环都会重新数一遍长度，总复杂度直接从 $O(N)$ 退化成 $O(N^2)$，字符串长度 $10^5$ 时必定超时。

三、⚠️ 复赛最致命的坑：size_t 无符号整数

这是 string::size() 最大的坑，经常导致 RE（运行时错误）或死循环！

size() 的返回值类型是 size_t，这是一个无符号整数（unsigned long long）。当你把它和 int 混用，尤其是做减法时，会触发"无符号整数下溢"。

错误示范 1（空字符串导致 RE）：

string s = "";
for (int i = 0; i < s.size() - 1; ++i) 
{
    // ...
}

解析：s.size() 是 0，s.size() - 1 会发生下溢，变成 18446744073709551615（$2^{64}-1$）。循环条件 i < 18446744073709551615 永远成立，导致数组越界 RE。

错误示范 2（倒序循环死循环）：

string s = "abc";
for (int i = s.size() - 1; i >= 0; --i)
{
    // ...
}

解析：当 i 减到 0 时，--i 变成 -1。但 i 是 int，s.size() - 1 是 size_t，比较时 int 会被转换成 size_t，-1 变成极大整数，条件 i >= 0 永远成立，死循环。

正确做法（教练强推）：在循环前，强制转换为 int 或赋值给 int 变量。

string s = "abc";
int len = (int)s.size(); // 或者 int len = s.length();
for (int i = 0; i < len; ++i) 
{
    // ...
}

// 倒序遍历
for (int i = (int)s.size() - 1; i >= 0; --i)
{
    // ...
}

四、补充知识点：length() 和 size()

  • 两者完全等价，时间复杂度都是 $O(1)$，返回值都是 size_t。
  • 早期 C++ 标准库为了兼容，同时提供了这两个函数。
  • 在竞赛中，推荐统一使用 s.size()，这也是大多数人的肌肉记忆。

五、教练的复赛优化建议

虽然 size() 是 $O(1)$，但如果你在双层循环（比如 $O(N^2)$ 的暴力枚举）的最内层频繁调用 s.size()，编译器可能不会自动把它提取到循环外。为了极致的常数优化，建议：

// 不推荐（每次循环都要调用函数）
for (int i = 0; i < s.size(); ++i) { ... }

// 推荐（把长度提取出来，防止无符号溢出且提速）
int len = (int)s.size();
for (int i = 0; i < len; ++i) { ... }

一句话总结：string::size() 是 $O(1)$，但千万别拿它和 int 直接做减法！用 int len = (int)s.size(); 保你复赛平安。

第九章：memset()

一、memset 的核心原理（必懂）

1. 底层是"按字节（Byte）赋值"

memset(void *s, int ch, size_t n) 的实现机制是：将内存 s 的前 n 个字节，逐个字节地设置为 ch 的二进制低 8 位。它根本不管你的数据类型是 int、double 还是结构体，它只认内存字节。

2. 为什么只能安全地赋 0 或 -1？

  • 赋 0：int 的 4 个字节全变成 0x00000000，结果就是整型 0；double 变成 0.0。
  • 赋 -1：在补码表示中，-1 的二进制是全 1（0xFFFFFFFF）。4 个字节全变成 0xFF，结果就是 -1。
  • 赋其他值（如 1）：memset(a, 1, sizeof(a)) 会让每个字节变成 0x01，一个 int 变成 0x01010101（即 16843009），绝不是 1。

二、0x3f 与 0x7f（竞赛必备知识）

在竞赛中，我们经常用 memset 给 int 数组赋"无穷大"，下面是最经典的对比：

填充值int a[0] 实际值double b[0] 实际值a[0] + a[0]（是否溢出）b[0] + b[0]
0x3f10611095670.000476792（极小值）2122219134（没溢出）0.000953585
0x7f21390621431.38242e+306（极大值）-16843010（溢出）2.76483e+306（没溢出）
极限值INT32_MAX: 2147483647DBL_MAX: 1.79769e+308——

1. 0x3f —— 竞赛中最安全的无穷大

memset(a, 0x3f, sizeof(a)) 会让 int 变成 0x3f3f3f3f，即 1061109567（约 $10^9$）。

为什么安全？因为 a[0] + a[0] = 2122219134，仍然小于 INT32_MAX（2147483647）。这意味着在两个"无穷大"相加时，不会发生整型溢出。这对于 Dijkstra、Floyd 等需要松弛操作的算法至关重要。

2. 0x7f —— 引发整数溢出的"炸弹"

memset(a, 0x7f, sizeof(a)) 会让 int 变成 0x7f7f7f7f，即 2139062143。

致命陷阱：a[0] + a[0] 变成了 -16843010。这是因为两个 0x7f7f7f7f 相加超出了 INT32_MAX，最高位进位变成了负数，导致整型溢出（Undefined Behavior）。如果此时比较 if (dist[u] + w < dist[v])，负数会直接破坏最短路算法。

3. double 数组的陷阱（不要用 memset 赋浮点数！）

0x3f 和 0x7f 给 double 赋的值分别是 0.0004... 和 1.38e+306。这是一种极其危险的做法。

0x7f 得到的 1.38e+306 确实很大，但如果题目需要做加法（比如 1.38e306 + 1.38e306），虽然表里没溢出，但如果题目数据再大一点，或者乘以某个常数，就会变成 inf（无穷大），导致 WA。

浮点数绝对不要用 memset 赋非 0 值！浮点数的无穷大应该用 for 循环赋值 1e18 或 1e9。

三、memset 的常见致命错误与避坑指南

1. sizeof 的误用

  • 错误：void func(int arr[]) { memset(arr, 0, sizeof(arr)); }
  • 原因：数组作为函数参数传递时会退化为指针，sizeof(arr) 计算的是指针的大小（8 字节），而不是数组总大小。
  • 正确做法：在函数外调用 memset(arr, 0, sizeof(arr))，或者显式传递数组的长度（如 memset(arr, 0, len * sizeof(int))）。

2. 结构体与 STL 容器的 memset

  • 如果结构体是 POD 类型（纯数据，无虚函数、无自定义构造函数），可以用 memset 置 0。
  • 但如果是 std::string、std::vector 或包含这些容器的结构体，绝对不能用 memset！这会把容器的内部指针置为 0，导致程序崩溃（RE）。

3. 多组数据的清空

在多组数据题目中，必须在每组数据前清空 dp 数组、vis 数组等。memset 是最快的工具，但要注意不要漏清或多清（比如把 head[] 邻接表数组清了没重新初始化边数 idx）。

四、memset 的时间复杂度

这是一个非常经典的面试题/竞赛常识题。

  • 理论时间复杂度：$O(n)$，其中 n 是传入的字节数（len）。
  • 常数与底层优化：虽然理论是 $O(n)$，但 memset 的底层实现是由编译器高度优化的。它通常会被编译器替换为内联汇编，使用 SIMD 指令（如 AVX、SSE 指令集）或 rep stosb 硬件指令，以按字（Word）或更宽的单位进行并行写入。
  • 实际表现：它的常数极小，执行速度比手写的 for 循环快得多（通常快 10 倍以上）。
  • ⚠️ 竞赛警告：不要因为常数小就滥用 memset。如果在时间复杂度为 $O(N^2)$ 的双重循环内部每次操作前都 memset 一个 $O(N)$ 的数组，总复杂度会退化为 $O(N^3)$ 导致 TLE（超时）。

五、总结口诀

memset 按字节，零和负一最安全。
0x3f 做无穷，相加不溢最稳当。
0x7f 是炸弹，相加溢出全完蛋。
浮点数别乱用，循环赋值才是王。
sizeof 防退化，多组数据莫忘清。

在复赛中，养成"数组只初始化为 0 或 -1，无穷大用 0x3f，浮点数用循环或 fill"的习惯，能帮你避开 90% 的初始化玄学 WA。

教练复赛终极叮嘱

  1. 写代码前：先看数据范围。$10^5$ 用 $O(N \log N)$，$10^6$ 用 $O(N^2)$，$10^9$ 用 $O(\log N)$ 或 $O(1)$。

  2. 交卷前 15 分钟：不要轻易改代码！很多选手在最后时刻改动了某个边界条件，导致从 100 分变成 0 分。

  3. 对拍是王道：如果觉得代码逻辑没问题但一直 WA，写一个暴力程序进行对拍，这是找 bug 最快的方法。
